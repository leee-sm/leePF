# 대시보드 서비스 설계

## 1. 목적과 설계 상태

관리자가 화면에서 대시보드를 만들고 편집·공개하면, 이용자는 로그인 후 공개된 대시보드를 조회하는 서비스다. 데이터 연결과 계산은 서버가 담당하고, 관리자는 업무 용어로 지표·차트·필터를 선택한다.

확정 방향은 React 프론트엔드, Python/FastAPI 백엔드, KTIS SSO 유지다. 이 문서는 구현을 위한 설계안이며 현재 구현된 코드는 SSO 모듈뿐이다. 대시보드 기능은 아직 구현되지 않았다.

첫 PoC는 제공된 재고 JSON으로 관리자 생성·편집·미리보기·공개와 이용자 조회를 시연한다. 실제 업무 API 연결은 이번 완료 조건이 아니다. MCP는 보류한다.

## 2. 사용자와 권한

| 역할 | 가능한 작업 |
|---|---|
| 이용자 / ROLE_USER | 공개된 대시보드 목록·상세 조회, 필터 변경, 재조회 |
| 관리자 / ROLE_SYSTEM | 이용자 기능 + 생성·편집·미리보기·공개·공개 중지·삭제 |

관리자는 시스템 전체 대시보드를 관리하는 기본안이다. 작성자는 이력으로 저장하며 소유자별 편집 제한은 두지 않는다. 관리자 역할 부여는 초기 운영 설정으로 처리하고 권한 관리 화면은 후속으로 둔다.

첫 PoC의 공개 대상은 활성 SSO 사용자 전체다. 데이터 소스는 이 대상에게 열람을 허용한 자료만 등록한다. 조직별 제한이 필요한 자료는 전체 공개하지 않으며, 권한 범위를 정하기 전까지 사용 대상에서 제외한다. 외부 비로그인 공유는 제공하지 않는다.

## 3. 첫 구현 범위

- SSO 로그인·사번 등록·서버 세션
- 이용자용 대시보드 목록과 조회 화면
- 관리자용 대시보드 목록, 생성, 편집, 미리보기
- 위젯 추가·설정·순서 변경·삭제와 제한된 폭 선택
- 공통 필터 설정, 조회·초기화·새로고침
- 초안 저장, 공개, 공개 중지, 삭제
- 서버에 등록된 데이터 소스 선택과 상태 확인
- 지표·필터 검증, 빈 결과·조회 실패·세션 만료 처리

대시보드 하나는 데이터 소스 하나를 사용한다. 여러 대시보드가 같은 소스를 사용할 수 있다. 첫 등록 소스는 `data/inventory_20260908.json`, `inventory_20260909.json`, `inventory_20260910.json`을 읽는 재고 소스다. 관리자는 재고 템플릿으로 시작하거나 위젯·필터를 수정할 수 있다. 파일 업로드·교체 화면은 이번 범위에 없다.

## 4. 관리자 흐름

1. 관리 목록에서 ‘새 대시보드’를 누른다.
2. 제목·설명·데이터 소스를 선택해 빈 초안을 만든다.
3. 편집기에서 위젯을 추가하고 지표·분류·제목·폭을 선택한다.
4. 이용자에게 보여줄 필터와 기본값을 설정한다.
5. 미리보기로 실제 조회 결과와 화면 배치를 확인한다.
6. 초안을 저장한다. 저장만으로 이용자 화면은 바뀌지 않는다.
7. ‘공개’를 누르면 설정 검증과 데이터 조회 확인 후 공개본에 반영한다.

공개 후에도 편집은 초안에만 적용한다. 수정 중인 대시보드의 이용자는 기존 공개본을 계속 본다. 공개 중지는 목록과 직접 접근을 모두 막으며, 초안과 마지막 공개 설정은 유지한다.

## 5. 이용자 흐름

SSO 로그인 → 대시보드 목록 → 상세 조회 → 필터 선택·조회 → 결과 확인 순서다.

목록에는 공개된 대시보드만 보인다. 제목과 설명으로 업무 목적을 구분하고, 상세에서는 조회 기간·지표·차트·표와 조회 시각을 확인한다. 이용자의 필터 변경은 본인 조회에만 적용되고 관리자 기본 설정을 바꾸지 않는다.

## 6. 설정과 공개 상태

| 상태 | 관리자에게 보이는 것 | 이용자에게 보이는 것 |
|---|---|---|
| 초안 | 편집·미리보기·공개·삭제 | 없음 |
| 공개 | 편집·재공개·공개 중지 | 마지막 공개본 |
| 공개 후 수정 중 | ‘미공개 변경 있음’ 표시 | 기존 공개본 |
| 공개 중지 | 편집·재공개·삭제 | 없음 |

초안과 공개본만 저장한다. 승인자 분리, 과거 버전 목록과 복구 기능은 초기 범위에 넣지 않는다. 삭제는 공개 중지 후 가능하며 확인창을 거친다. 삭제된 대시보드는 복원 기능을 제공하지 않는다.

## 7. 위젯과 편집 범위

| 위젯 | 설정 항목 | 사용 예 |
|---|---|---|
| 지표 카드 | 지표, 제목, 단위·소수점 표시 | 전체 재고 수량 |
| 막대 차트 | 분류, 지표, 정렬, 상위 항목 수 | 제조사별 재고 |
| 집계 표 | 분류 항목, 지표, 정렬 | 거래처·모델별 수량 |

재고 템플릿은 전체 재고 카드, 제조사별 막대 차트, 모델별 상위 10개 막대 차트, 제조사·모델별 집계 표와 시작일·종료일·제조사·모델 필터로 구성한다. 기본 조회 범위는 실제 조회 가능한 가장 이른 날짜부터 가장 늦은 날짜까지다. 개요와 기존 차트·표는 종료일 재고를 표시하고, 변화량은 같은 제조사·모델 조건을 적용한 시작일 재고와 비교한다. 선 그래프는 선택 범위의 실제 스냅샷만 보여주며 날짜별 수량을 합산하지 않는다. 관리자는 위젯과 필터를 수정·삭제하고 다른 대시보드도 만들 수 있다. 지표는 서버에서 정의한 목록에서 고르며 임의 수식·SQL·스크립트 입력은 제공하지 않는다.

편집기는 12열 격자를 사용하며 폭은 1/4·1/3·1/2·전체 중 고른다. 위젯 순서는 위·아래 이동으로 바꾼다. 자유 좌표 배치, 겹치기, 드래그 크기 조절은 후속이다.

초기 제한 제안은 대시보드당 위젯 12개, 공통 필터 6개다. 제한은 화면 복잡도와 한 번의 조회 비용을 관리하기 위한 값으로 구현 시 서버에서도 검사한다.

## 8. 초기 범위에서 제외

MCP, AI 기능, 자유 조인, 사용자 입력 URL 연결, 데이터 연결 관리 화면, JSON 업로드, 가격 지표, 자유 배치 빌더, 실시간 공동 편집, 조직·그룹별 공개, 게시 이력 복구, 자동 주기 갱신은 후속으로 둔다. 재고 화면에는 `outPassovrDay` 원본 경과일 후보 필드로 30~89일과 90일 이상을 중복 없이 집계하는 요약을 제공하되, 실제 재고 보유 기간이라는 업무 해석은 원천 담당자 확인 후 확정한다.

필요한 편집·공개 기능은 이번에 구현하되, 별도 워크플로 엔진이나 범용 플러그인 구조는 만들지 않는다.

## 9. 구현 완료 조건

- 관리자가 코드 수정 없이 등록된 소스로 대시보드를 생성·편집·공개한다.
- 이용자는 공개본만 조회하며 초안과 관리자 API에 접근할 수 없다.
- 초안 변경·저장 중에도 기존 공개 화면이 유지된다.
- 같은 조건의 미리보기와 공개 화면이 같은 계산 결과를 보여준다.
- 필터가 모든 위젯에 일관되게 적용되고 원천 결과와 계산이 일치한다.
- 저장 충돌, 공개 실패, 빈 결과, 데이터 장애, 세션 만료를 구분한다.
- 공개 중지 후 목록과 데이터 조회가 모두 차단된다.
- 재고 템플릿의 전체 수량은 선택한 날짜의 행 수이며 동일 내용의 행도 각각 센다. 제조사·모델별 집계와 필터도 같은 행 집합을 사용한다.
- 2026-09-08 샘플의 0건은 정상 조회 결과로 표시하고 조회 실패와 구분한다.
- 개발 PC와 사내 서버에서 Docker로 실행할 수 있다.

실제 KTIS SSO는 시연 환경의 허브·OTT 교환·callback 설정이 준비되면 검증한다. 준비되지 않으면 로컬 개발용 로그인으로 관리자·이용자 흐름을 시연한다. 실제 SSO와 원천 API 검증은 샘플 시연과 구분해 기록한다.

## 10. 실제 데이터 연결 전에 확인할 사항

실제 원천 API 연결로 넘어갈 때 주소·인증·응답·조회 가능 날짜를 확인한다. 샘플 PoC의 재고 수량·가격 0·공개 대상 해석은 [데이터 연동 기준](inventory-dataset-contract-draft.md)에 기록한다. 경과일 요약은 원본 후보 필드의 기준값으로 표시하고 0을 별도로 안내한다. 재고 보유 기간으로 해석하기 전 원천 담당자에게 필드 의미와 0의 업무 의미를 확인한다.
